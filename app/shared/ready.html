Are we ready to present?

Presentable today — not finished, and this page says which is which.

Every step of the walkthrough below runs on the live site today — with TWO exceptions, each called out in red inside the walkthrough itself and again below. First: a member's booking cannot reach the Dashboard's meters, because the Dashboard still builds its own studio. Second, found by a second audit on August 22, 2026: the assistant cannot answer on the deployed site, because it posts every question to an address the static build does not publish. This paragraph said ONE exception until that audit, and step 5 below claimed the assistant answered — so the board was overstating itself in exactly the way it warns against. Presenting the red as red is the discipline — and if the verdict ever claims more than the proofs show, the verdict is what gets fixed.

The one picture (say it pointing, one sentence per box)

60 members → 10 gone quiet → 1 already booked back in → 9 drafts for staff to send — every drop is a decision the middle box made, measured today.

1. Everything starts as one member's tap or visit, recorded once, in their own browser.

2. The studio keeps all of it in one trail and works out what to do next.

3. Staff get the week filled, members get straight answers, and the quiet get a personal draft a person sends.

The five-minute walkthrough

  1. Open the front door. It speaks to a member — book, ask, and "never go unnoticed" — and the pulse line beats.
  2. Sign in from the top bar as a member: the front door greets them by name and takes them straight to their classes; the same persona follows every page.
  3. Book a class Booking — the week day by day, spots left, and a confirmation naming the class, time, and instructor. Your reservations appear under the schedule with a cancel on each.
  4. Open the Dashboard Dashboard — the week's fill rates and the classes needing attention. Say the gap out loud here: this board still builds its own studio, so the booking from step 3 is not on it yet — one config line away, and the honest thing to show.
  5. Ask the assistant Support a schedule question. Say the second gap out loud here: on the deployed site this answers nothing — every question is posted to an address a static build does not publish, so the page states that support is unavailable rather than inventing a reply. Running locally with a key, it answers from the current schedule and states its refusals.
  6. Sign in as Front Desk and open Re-engagement Re-engage — the quiet ranked with evidence; a member who booked back in is named and left alone; copy the draft.
  7. Close on the story: storytold — the five beats and the map where every finished hand-off literally fires.

  • The eight dead root files are gone — the site we had before Pages switched to publishing app/. This entry read "still sit in the repo root" after they had been removed, which is the failure this board exists to avoid; the root now holds the contract and nothing else, and scripts/check-published.mjs counts it every run so the claim is not prose.
  • The deploy boundary is a setting, not a fact — GitHub's legacy builder still records the repo root as its Pages source underneath the Actions deploy. If anyone flips Settings → Pages → Source back, those eight dead files become the live site and app/ demotes to a subfolder. The code still cannot PREVENT that — no workflow can overrule a repo setting — but since 2026-08-22 it no longer stays quiet about it: the build reads the Pages source, publishes only when it is GitHub Actions, and writes “deploy skipped — Pages source is X” into the run summary otherwise. A failed read of that setting now stops the run instead of being folded into a green one. Worth knowing before anyone touches that screen.
  • Two law ratifications — the appearance amendment and the audience law await the four builders' explicit yes on their PRs.
